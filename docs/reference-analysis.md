# 参考曲の分析(YouTube → 音声 → 音源分離 → MIDI → 雰囲気の言語化)

目的: 「こんな雰囲気の曲を作りたい」を、参考曲の**抽象的な特徴**に翻訳して `spec` に反映する。コーチの対話の材料であり、曲をまねるための機能ではない。

## 使い方
`/reference <song> <YouTube URL>`、または `scripts/reference_run.sh <song> <url>`。
`scripts/reference_run.sh` は次の4段階を順に実行する(個別実行も可):

| 段階 | スクリプト | 出力(`projects/<song>/reference/<video-id>/`) |
|---|---|---|
| 取得 | `reference_fetch.sh` | `audio.wav`、`source.json`(タイトル等) |
| 音源分離 | `reference_separate.py`(Demucs **htdemucs_6s**。`--model htdemucs` で4パート) | `stems/{drums,bass,other,vocals,guitar,piano}.wav`(コード・キー・リズムの推定用) |
| 書き起こし | `reference_to_midi.py`(**MuScriptor**、多楽器対応) | `transcription.mid`(楽器ごとのトラック+ドラム) |
| 分析 | `reference_analyze.py`(librosa) | `analysis.json`、`analysis.md` |

音源分離は初回にモデル(約80MB)を取得する。CPU で曲の長さの0.5〜1倍ほどかかる。省く場合は `REF_SEPARATE=0`。
必要なもの: `brew install yt-dlp ffmpeg`。Python 依存は `uv sync --group reference`(`uv run --group reference` で自動)。

### MuScriptor の準備(初回のみ。認証はユーザー自身が実行する)
1. Hugging Face にログインし、https://huggingface.co/MuScriptor/muscriptor-medium でライセンス(**CC BY-NC 4.0、非商用**)に同意(自動承認)。large を使うなら large も別に同意。
2. `uvx hf auth login`(トークンは `~/.cache/huggingface/` に保存され、リポジトリには入らない。値をファイルやログに書かない)。

MuScriptor は `uvx --from muscriptor==0.3.0` で版を固定して実行し、プロジェクトの Python 環境とは分離される。初回は重みを取得する。medium で CPU の場合、42秒の曲に約2分、191秒の曲に約110秒かかった(曲の長さの0.6〜3倍と幅がある)。`--model small|medium|large` で選べる。

## 分析する特徴
テンポ / キー(長調・短調)/ 小節ごとのコード(ローマ数字=機能で表示。短調は平行長調基準)/ 盛り上がりの形(8分割の音量)/ 音の明るさ / 刻みの細かさ / 書き起こし MIDI の音域・密度。
旋律・歌詞・音符列そのものは出力しない。

## 音源分離の効果(合成音源での検証)
正解の分かる16小節(C-G-Am-F ×4、100 BPM、ドラム・ベース・ピアノ・メロディ)で比較した結果:

| 項目 | 分離なし | 分離あり |
|---|---|---|
| コード(小節ごと、位置ずれ許容) | 14/16。Am の重複など進行が乱れる | **16/16**。C-G-Am-F が全周で一致 |
| テンポ | 99.4 BPM | 99.4 BPM(正解100) |
| キー | C 長調 | A 短調(平行調。ローマ数字の基準は同じ) |

分離ありのコード推定は、**根音をベースのパート、長調/短調を和音パート(other)の3度**から決める。ベースの倍音(5倍音=長3度)に惹かれて A を A(長)と誤る問題を避けるため。
(Basic Pitch での検証)ベースの MIDI 書き起こしは分離しても低域で不安定(音が抜ける)。しきい値を下げると増えるのは多くがノイズで、採用していない。**MIDI は傾向把握用、コードの根拠は音声のクロマ**と考える。実際の楽曲(実楽器・歌入り・転調)での精度は未検証。

## 書き起こしモデルの比較(MuScriptor を採用した根拠)
同じ合成音源(正解 MIDI あり)で、音符単位の F1(開始 ±50ms、音高一致、オクターブ無視、ドラム除外)を比べた。

| 方式 | 適合率 | 再現率 | F1 |
|---|---|---|---|
| Basic Pitch(分離なし) | 0.75 | 0.33 | 0.46 |
| Basic Pitch + Demucs 分離 | 0.76 | 0.61 | 0.68 |
| **MuScriptor medium**(分離なし) | **0.91** | 0.58 | **0.71** |

- パート別に正解の音を拾えた割合は、メロディ 99%(Basic Pitch 分離あり 96%)、ベース 25%(同 30%)、和音 25%(同 38%)、ドラム打点 42%(Basic Pitch は非対応)。
- 全体の F1 は同程度で、**余計な音が少なく、ドラムと楽器名の推定が得られる**点で MuScriptor に置き換えた。ベース・和音の取りこぼしは残るので、コードの根拠は MIDI でなく音声のクロマ(上記)に置く。
- 楽器名の推定は不正確なことがある(メロディをギターと判定した例)。検証は合成音源1曲のみ。実曲での精度は未検証。

## 実際の曲での試行(Kevin MacLeod "Sunshine"、CC BY、3分26秒)
取得→分離→書き起こし→分析まで約35秒で通った。結果と、そこで見つけた弱点への対処:

- キーが **A 短調**と出たが、推定コードは A / D(長調)の交替と F / C だった。音の分布だけでキーを決めていたため。→ **コード列がキーの音階に収まる割合**も加味して決め直すようにし、**A 長調(I–IV と、同主短調から借りた ♭VI・♭III)**に修正された。
- A・D の3度が曖昧な小節は長/短を断定せず「A5」のように**3度不明**で表す(差が小さい場合のみ)。
- ボーカルがほぼ無音の曲では、他の楽器の混ざり込みで偽のボーカル MIDI が出ていた。→ 無音に近いパートは書き起こさない。
- 正解が分かる曲ではないので、**実曲での正答率は測れていない**。出力はあくまで仮説で、耳で確認する。

## 6パート分離(htdemucs_6s)について
- 既定は 6 パート版。ピアノとギターが `other` から分かれる。コード・キーの推定は bass と、other + guitar + piano の合算を使う。
- 開発元が実験的としており、**ピアノ・ギターの分離は不安定**。実曲(ギター中心の曲)では、書き起こし上は主役のギターが guitar パートには 1% しか入らず、`other` に残った。ピアノは約 6% 分離されたが、取りこぼしや漏れは未検証(聴いて確認する)。
- 分離を変えてもコード進行の推定精度は変わらなかった(キーの音階に収まるコードの割合 0.63 → 0.61)。コードの散らばりの主因は拍の揺れ(固定の小節区切りがずれる)と考えられる。
- 4 パート版が欲しい場合は `reference_separate.py ... --model htdemucs`。

## 精度の限界(必ずユーザーに伝える)
- 複数楽器が混ざった音声の書き起こしは不完全。MIDI は音域や密度の傾向を見る目安。
- テンポは倍/半分に誤検出することがある。コード推定は旋律や転調で外れる。
- 推定値はユーザーの耳で確認してから spec に反映する。

## 守ること(厳守)
- **私的な参考分析に限る**。YouTube の利用規約と著作権法を守り、取得する権利のあるコンテンツだけを対象にする。ダウンロードの責任はユーザーにある。
- 取得した音声・書き起こし MIDI は**コミット・公開・再配布しない**(`.gitignore` 済み)。分析結果(`analysis.md/json`)は抽象的な数値のみ。
- 参考曲の**旋律・歌詞・特徴的なリズムパターンを複製しない**。取り入れるのはテンポ感・キーの長短・コード機能の並び・盛り上がりの設計などの一般的な要素まで。
- 「AI が学習する」は、分析結果を材料にコーチが対話することを指す。モデルの学習・ファインチューニングはしない。
- NEUTRINO の出力音声・中間データを参考曲として分析しない(`docs/licensing.md`)。
